الراوتر الوهمي mockportal.py

MockPortal هو سيرفر HTTP كامل على 127.0.0.1 يتصرف كبوابة أسر، ويُستخدم كـcontext manager (with MockPortal(...) as portal:). كل حالة فشل حقيقية في العالم لها علم هنا:

المعاملالافتراضيالحالة التي يحاكيها
valid_cards—مجموعة البطاقات الصالحة
pass_mode"same"same / empty / chap
method"post"بوابة GET أم POST
dynamicTrueصفحة الرفض تحتوي رمزاً/وقتاً يتغير في كل رد
ban_after / ban_seconds0 / 0بعد كم فشل يُحجب، وهل يزول الحجب (0 = لا يزول أبداً)
rate_limit_after0يرد 429 بعد هذا العدد
drop_every / drop_after0 / 0يقطع الاتصال كل n طلباً، أو بعد n طلباً تماماً
chapFalseيقدّم md5.js ويتوقع تجزئة CHAP
prefix / length"02" / 6شكل البطاقات المتوقَّع
error_text"invalid username or password"عبارة الرفض
hide_successFalseأخبث حالة: البطاقة تُدخل فعلاً لكن الراوتر يردّ بصفحة الرفض — وحده المراقب يكشفها
require_sessionFalseيرفض POST بلا كوكي جلسة ورمز من صفحة الدخول (ما يفعله المتصفح تلقائياً)
reject_shapeFalseيرفض شكل الطلب (400) بدل رفض البطاقة
success_pageFalseيردّ بصفحة نجاح واضحة
unknown_success_pageFalseيقبل البطاقة ويفتح الشبكة لكن يردّ بصفحة 200 غير موسومة — لا يمكن إثباتها بدون فحص إنترنت
global_online_login_pageFalseبعد فتح الجلسة يعيد صفحة الحالة/الدخول الناجح لكل طلب لاحق ⇒ يولّد تحققات كاذبة تحت التشغيل المتوازي

خصائصه المفيدة في الاختبارات:

  • portal.url ⇒ http://127.0.0.1:<منفذ>/login، وportal.base ⇒ الجذر.
  • portal.state.tokens ⇒ الرموز التي وزّعها (لاختبار الإحماء).
  • portal.state.bad_requests ⇒ كم طلباً ردّ عليه بـ400 (لاختبار «شكل الطلب مرفوض»).
  • صفحات HTML جاهزة: CARD_PAGE, BAN_PAGE, RATE_PAGE, SUCCESS_PAGE.
  • يوجد أيضاً مسار /generate_204 حتى تستطيع KIRAPASS_INTERNET_CHECKS أن «ترى إنترنت» محلياً.

فحص الرحلة الكاملة tools/checks/web_e2e.py

ليس جزءاً من مجموعة unittest: سكربت مستقل يمرّ عبر الـHTTP API نفسه الذي تستخدمه الواجهة. يحتاج ثلاثة أشياء تعمل معاً:

# 1) بوابة تدريب
python3 tools/practice_portal.py --port 8898 --card 020124042 \
    --pass-mode empty --ban-after 5000

# 2) الأداة نفسها (مع فحص إنترنت محلي)
KIRAPASS_INTERNET_CHECKS="http://127.0.0.1:8898/generate_204|204" \
    python3 KiraPass.py --host 0.0.0.0 --port 8770 --token kirapass --no-browser

# 3) الفحص
python3 tools/checks/web_e2e.py

الخطوات التي ينفّذها، وهي نفسها خطوات المستخدم:

  1. /api/scan — يقرأ صفحة الدخول ويطبع الحالة والأسلوب وأسماء الحقول وCHAP وحالة الإنترنت.
  2. /api/format/preview ثم /api/profiles/save — يبني البروفايل كما يبنيه المعالج.
  3. /api/calibrate كمهمة خلفية + /api/job للاستطلاع — يطبع كل خطوة ونتيجة البصمة.
  4. /api/run/start (1000 محاولة، 8 مسارات، تحقق، إيقاف تلقائي) + استطلاع /api/run/status?since= — يطبع العدّادات والأسباب والتقدم وأنواع الأخطاء والإصابات.
  5. الاستئناف: تشغيلان من 150 محاولة، ويطالب بأن space_pos = 150 ثم 300 وأن walk_a/walk_b لم يتغيرا؛ وإلا SystemExit(1).
المعاملات الموضعية: web_e2e.py [BASE] [TOKEN] [PORTAL] — الافتراضي http://127.0.0.1:8770 وkirapass وhttp://127.0.0.1:8898/login.

كيف تكتب اختباراً جديداً

  1. اختر الطبقة: منطق صرف ⇒ unittest؛ سلوك محرك كامل ⇒ سيناريو في selftest.py (ويُضاف تلقائياً إلى ScenarioTests)؛ واجهة/ـAPI ⇒ web_e2e.py.
  2. استخدم MockPortal — لا شبكة خارجية أبداً. إن احتجت «إنترنت»، وجّه KIRAPASS_INTERNET_CHECKS إلى …/generate_204.
  3. لا تكتب في kirapass_data/: الاختبارات توجّه config.set_data_dir() إلى مجلد مؤقت عند استيراد الملف. إن كتبت سيناريو جديداً فهو يرث ذلك تلقائياً.
  4. اجعل الفشل مقروءاً: مرّر رسالة في assert* أو املأ Result.detail بالأرقام التي كنت ستقارنها.
  5. سمِّ الاختبار بما يقوله لا بما يختبره: test_a_card_that_got_no_answer_is_asked_again — هذا أسلوب الملف.
  6. شغّل الفئة وحدها أولاً، ثم المجموعة كلها.

ما الذي لا تغطيه الاختبارات (كن صادقاً مع نفسك)

  • لا اختبار لـweb/ui.js في متصفح: UIIntegrityTests يفحص النص (المعرّفات والترجمات ووجود عبارات معينة) ولا ينفّذ JavaScript. تغييرات السلوك في الواجهة تحتاج فتح الصفحة يدوياً على بوابة تدريب.
  • لا اختبار لـui.css إطلاقاً.
  • لا اختبارات أداء/حمل حقيقية: السرعات في الاختبارات مقاسة على راوتر وهمي محلي.
  • لا اختبار TLS حقيقي (VERIFY_TLS = False ولا بوابة https وهمية).
  • لا اختبارات للخيوط خارج المحرك: web/server.py يُختبر عبر web_e2e.py يدوياً فقط.
